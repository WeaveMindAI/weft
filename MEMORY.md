# Project Memory: weft
Durable facts for this repo, shared by every assistant setup. Each entry = one or two tight lines. Claude Code imports this file at session start; Kilo Code loads it through `.kilo/kilo.json`. General rules are harness-specific: Claude Code's live in `.claude/CLAUDE.md` and its mode skills (`.claude/skills/mode-*/SKILL.md`), Kilo's in `.kilo/agent/working-partner.md` and `.kilo/skills/mode-*/SKILL.md`. Add new entries inline as `##`. Keep this small.

## Schema: canonical CREATE TABLE plus generated migrations
Every table is written down twice and both are kept. The canonical `CREATE TABLE` lives in Rust on a `SchemaGroup` next to its code (edit in place; builds a fresh database). One SQL file per change under `crates/weft-task-store/migrations/<group>/` carries an existing database forward; each database records what it ran in `weft_migration`, so any old database reaches today and two branches converge whichever way they merge. The crate's build script walks that directory, so a file being there IS its registration: nothing lists it, no Rust changes, and it travels with the crate into every build context. NEVER hand-write a migration and NEVER edit a released one (the boot refuses it, checksummed). The flow: change the DDL, then `./setup.sh --migration <name> --release`. ONE command, always: it writes the released file, runs it on your database, and records it as applied, whether or not a draft came first. NEVER tell the [user] to run two. The draft pass (`./setup.sh --migration <name>` with no `--release`) exists only for iterating on a table across several edits (a gitignored DRAFT under `drafts/`, applied as you go, your data kept); the release then collapses every draft into one file. Each group also has a frozen `origin.sql` (its DDL at ship time, written automatically); the `schema_agreement` test replays origin+released (drafts excluded, so an unreleased draft fails CI) and compares against the canonical build. Changing the DDL with no migration fails the boot printing reset SQL. Prefer additive changes; drop a column in a later release than the one that stopped reading it. The history restarted once, at the move off Kubernetes (every `origin.sql` re-frozen, older migrations deleted): the boot refuses a database from before it, and `scripts/scrub-old-install.sh` wipes that one.

## Runtime tiers: Listener / Supervisor / Dispatcher / Worker
Four tiers, one role each; the broker is not a tier but the scoped door to Postgres for every role except the dispatcher. **Listener:** holds signals and relays their fires to the dispatcher (the dispatcher calls it; its own fires go back as `fire_signal` tasks through the broker); pooled + tenant-agnostic; never decides/spawns/touches the journal. A signal whose kind keeps a connection open (`BetweenFires::Holds`, decided per signal at `/prepare`, stored as `signal.holds`) is held by a **holder**: the listener's code where something stays up, claiming rows by lease through the broker (`weft_listener::hold`); on GCP a worker pool the dispatcher sizes from the held rows, locally the one process. **Supervisor:** pooled + tenant-agnostic; exclusive `infra_owner` lease per project so one supervisor applies a project's infra at a time, through the platform's `InfraHost`. **Dispatcher:** pure routing + lifecycle + placement; persists to Postgres; never executes node logic. **Worker:** runs the compiled project binary, one per program, multiplexes executions, idle-shuts-down. Listener is the kind-aware processor (kinds live in `crates/weft-listener/src/kinds/`); dispatcher is pure transport and acts on a kind-agnostic `ProcessTarget` (`weft_core::signal::listener_protocol`). New signal kinds = listener code only; never a dispatcher-side kind branch.

## Dispatcher coordination through the DB
Dispatcher replicas are stateless coordination-wise: Postgres is the single source of truth, process RAM is just optimization. Ownership = DB leases (any replica claims an expired one). Reconnect to a sibling replica must rebuild from DB (no state across the gap). Before adding an in-RAM mutex/dashmap/counter on `DispatcherState`, ask "what if a sibling replica handles the next request?": if that means stale reads/lost updates, it belongs in Postgres. N replicas is the target; a single replica is the degenerate case.

## Language vs node separation
The language is generic: compiler/dispatcher/engine/shared infra never contain node-specific knowledge (no hardcoded field names, no `if node is X`). Nodes do no plumbing: a node's code only does its own logic; translating it into language concepts (triggers, URLs, suspensions, sidecar manifests) is the language's job. When a node needs something the language lacks, build the general mechanism first, then have the node use it through the ctx. The same holds for WORDS: docs, Tangle prompts and code comments outside a node's own folder teach the general mechanism, and may name a node only as an example of it ("a node that keeps a growing value takes a file, like LlmInference's conversation"), never as the subject ("LlmInference's historyFile does X"). A sentence that only makes sense for one node belongs in that node's own `metadata.json` description, where the editor and Tangle read it.

## Execution id = one execution
`ExecutionId` (`weft_core::ExecutionId = Uuid`) IS one execution: minted at `ExecutionStarted`, spent on terminate; a re-run is a NEW id. No retry-across-executions, no per-execution attempt cap (a give-up-after-N concept would be per-PROJECT, out of scope).

## Don't timeout user-facing long operations
Real workflows (LLM pipelines, infra builds, human-in-the-loop, executions) can run hours/days. No deadlines on user-controlled waits (build/deploy/infra/execution/drain/user node code); make stuck-state legible (periodic breadcrumb + a documented recovery like Ctrl+C / `weft stop`). Deadlines only on internal service-to-service waits the user can't control.

## Every fix and feature ends with setup.sh and the e2e that cover it
You run these yourself, every time the code is done (not only at the end of a session), after the unit tests, `scripts/run-db-tests.sh`, clippy, `svelte-check` and `pnpm run compile` for the change are green. Background each one.
1. Install: `./setup.sh`, plus `--public-url` when `~/.local/share/weft/public-url-enabled` exists (the tunnel is on). A change only to the runtime can skip this: the e2e runner runs `setup.sh --cli --daemon` first anyway.
2. Pick the tests: ONLY the e2e tests you added plus the ones that exercise the behavior you changed, each named `file::test` (never a whole file when one test covers it; one test per changed path is enough), even at the very end of a session. The same holds for `scripts/run-db-tests.sh <crate> <test-name>`: named tests only. Never the whole suite, even for a change in a shared tier: some tests spend real money, and a full run is the [user]'s call alone. A test that costs money is fine to run when it is one of those; never run it otherwise.
3. Run: `scripts/run-e2e.sh --keep-going <file> <file::test> ...` (always name the tests; nothing after the flags runs everything, which you never do). The defaults are the recommended limits on this 24-core machine: 16 tests at once and 4 compile lanes; lower `-j` on a smaller machine, raise `WEFT_COMPILE_LANES` only with disk to spare (about 2GB each, in the install's BuildKit volume; `weft daemon start` reads it, so the e2e runner's own install picks it up).
4. Until green: read the failing test's log and `.post-mortem/` under `~/.local/share/weft/e2e/run/`, fix the cause (a flaky test is a bug in the code under test, UNLESS the failure is in the local rig itself: docker, the machine's load; then rerun that one test alone, and if it passes, it is done: never chase a rig flake), then `scripts/run-e2e.sh --keep-going --failed`, which runs only what has not passed yet. When nothing is left, rerun the whole selection from step 2 once, so the fixes are proven not to have broken what passed before them.
5. The runner ends every run (pass or fail) with `weft clean --images --all`, which also drops the compile cache this checkout moved off; if you stopped a run by hand or ran e2e binaries yourself, run it before you finish. A long session of rebuilds otherwise leaves tens of GB behind.
The e2e README (`crates/weft-e2e/README.md`) has the runner's flags and how to read a failure.
Waiting on any of these: start it with `run_in_background` and wait for its completion notice, and in the same reply give the [user] the exact file to `tail -f` or command to run to follow it live (the background output file, `~/.local/share/weft/e2e/run/<file>::<test>.log`, `~/.local/share/weft/setup-runs.log`), so they can watch it themselves. Never write your own wait loop like `until ! pgrep -f "<script>"`: `pgrep -f` matches the loop's own command line, which contains that text, so the loop never ends (this once cost an hour). If you must look before the notice, one check with a timeout of 3 minutes at most, then look again. Nothing here runs longer than that, and no single e2e test runs longer than 5 minutes: the runner stops it and reports it `SLOW`.

## Tangle folders are copies on purpose
`tangle/<assistant>/` holds one independent copy of the Tangle persona, skills, specialists and commands per assistant (eleven folders: the ten named ones plus `fallback/`). They start identical and are MEANT to drift as each is tuned for its host: no shared source, no SYNC markers, no CI check, and deduplicating them is wrong. The line: what Tangle IS must hold in every folder (shape the graph first, read a node's real interface, keep a level small, fail loudly, report plainly); how it is SAID may differ per assistant. `fallback/` installs its root `AGENTS.md` ONLY when no named assistant matched, because Cursor, Cline and Gemini read a root `AGENTS.md` on top of their own persona file rather than instead of it.

## A URL a client will fetch is built from that client's request, never from config
One install answers at several addresses at once (the loopback port, the tunnel hostname, a domain), so ANY server-side constant is wrong for every caller arriving at one of the others, and the breakage is invisible until someone clicks. Rule: if the client that ASKED is the client that will FETCH, build the link from that request's own `Host` + `X-Forwarded-Proto` (`weft_core::net::request_base_url`, wrapped as `storage::LinkBase::for_request`); the configured base is only the no-`Host` fallback. Only a link handed to a THIRD party (a provider's webhook target, a pasted address) uses the configured `external_base_url()`, because the requester's host says nothing about what that third party reaches. This is safe because such links are capability URLs whose token is the credential. Symptom when violated: "Media expired or unavailable" in the graph/extension, links pointing at 127.0.0.1. Never re-fix this by adding another env var or another audience constant; that is the bandaid that keeps regrowing.

## Every feature lands on three fronts: levers, defaults, protection
Before building anything, answer all three, and say so. **Levers**: what a person can reach and from where (a node setting, a CLI flag, a graph control, a ctx call, a `metadata.json` key, a word in the language). Name the lever and where it lives; a knob nobody can turn is not a lever, a knob nobody needs is clutter. **Defaults**: what everybody gets without asking, which is the part nobody should have to know exists. Two questions: is it tedious and useful to make somebody fill it in every time, and is there a value right for almost everybody? Yes to both, set it and keep the lever. Never invent a default to paper over a setting that honestly depends on the case: if leaving it unset is legitimate, it stays explicit and optional and the VALIDATION is what makes the bad shape impossible. A hidden default that is right half the time is worse than a refusal naming what is missing. **Protection**: as long as there is a way to build it properly, the bad shape is refused and the message points at the right one, at the earliest place that can see it (compiler, parser, a node's metadata rules, and a runtime floor where nothing earlier can). An obvious footgun (an infinite loop, a run that waits forever on somebody gone) must be impossible to configure, not warned about. Nodes are written by users, so a problem found in a node (a costly pattern, a wrong shape) is fixed with a weft default or protection that makes any node written that way right; only where weft cannot, the docs and the Tangle prompts teach the right pattern. The full wording: `docs/src/thinking/how-we-decide.md`.

## Every slow command runs in the background, with a realistic cap
Anything that can take more than a few seconds runs with `run_in_background`: builds, tests, installs, and cloud work too (`gcloud ... create`, a Cloud SQL instance, `terraform apply`, project or machine creation). Never in the foreground, never "just this once"; an unknown duration counts as slow. Every wait on it is capped at how long that thing normally takes (a cargo check about a minute, an e2e test at most 5, a Cloud SQL create about 10), never a catch-all like 25 minutes: at the cap, look at what it is doing (its output, its operation's state) and tell the [user]. A foreground `gcloud sql instances create` once sat silent for many minutes until the [user] backgrounded it by hand.
